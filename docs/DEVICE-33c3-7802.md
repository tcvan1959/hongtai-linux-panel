# Verified device: `33c3:7802`

## USB identity

- Vendor ID: `0x33c3`
- Product ID: `0x7802`
- Manufacturer string: `HONGTAI`
- Product string: `MONITOR`
- Linux driver: `cdc_acm`
- Serial endpoint observed: `/dev/ttyACM0`
- Example stable device link:
  `/dev/serial/by-id/usb-HONGTAI_MONITOR_SERIAL_PLACEHOLDER-if00`

`SERIAL_PLACEHOLDER` is synthetic. Users must substitute the by-id name
detected on their own system.

The Ubuntu user was verified able to open and close the serial endpoint without
`sudo`.

## Device-information response

Command `0x06` returned the following verified values from the physical panel:

- UID: present and parseable; the individual unit's value is not published
- Model: `TXW818-ST7796-3.5inch-hor`
- Width: `480`
- Height: `320`
- Firmware version: `3.2`
- Brightness: `80`
- Angle: `0`

The packaged query tool repeated this result successfully on August 17, 2026.
Firmware 3.2 returned the values under a top-level JSON `data` object; the
typed parser supports both that nested form and the previously documented
flat form.

Some response fields can vary with configuration. Software should query the
panel rather than treating these values as universal Hongtai defaults.

## Verified display operation

A generated 480×320 JPEG was transmitted from Linux and appeared correctly on
the physical panel. During that test:

- the live pipeline accepted command `0x11`;
- the JPEG data envelope and terminator were accepted;
- periodic `0x11` commands held the display active; and
- command `0x21` released the live pipeline but left the panel blank.

The blank-after-close behavior is the reason the static-image tool does not
send `0x21` unless the user explicitly requests `--release`.

On August 19, 2026, one bounded exit-sequence test was performed after a
healthy cold boot and was not repeated. The exact sequence was:

```text
pipeline reset | 0x11 | one verified JPEG | FF D9 FF D9 | 0x11
wait 3 seconds | standalone FF D9 FF D9 | 0x21 | close serial port
```

The test frame appeared correctly, but the panel remained blank after the
standalone terminator and close command. This is negative physical evidence:
`FF D9 FF D9` followed by `0x21` does not restore the firmware's default
animation on this `33c3:7802`, model `TXW818-ST7796-3.5inch-hor`, firmware 3.2
unit. It does not identify a replacement playback command. Do not infer or test
speculative media or filesystem commands from this result.

On August 20, 2026, a separately authorized physical test verified command
`0x01` (`CMD_RESTART`) on this same device and firmware. One command caused a
board-level reboot and USB disconnect/re-enumeration, restored the
factory/default animation, and left the re-enumerated panel in a healthy state
that accepted a device-information query. This is a reboot-based return to the
default display, not evidence that `0x21` resumes internal playback or that a
non-reboot media-selection command is known.

The restart invalidates the open serial connection. Software using it must
expect the temporary tty/USB disappearance, send it only once, and must not
automatically retry, reopen, query, reset, or unbind/rebind if the device does
not return as expected.

On August 17, 2026, the packaged test-pattern command successfully transmitted
a 17,763-byte JPEG and maintained the live pipeline for 15 seconds without
sending the close command. The physical image appeared correctly, then cleared
after the process stopped. Continuous `0x11` refresh commands are therefore a
verified requirement for retaining even a static image.

The repository retains an experimental foreground service that can locate a
stable device link and maintain refresh commands. Its reconnect and automatic
login paths are unsupported, disabled by default, outside accepted v1, and not
qualified for unattended use on firmware 3.2.

An earlier foreground-service experiment auto-discovered the verified link,
opened the panel, restored the test pattern, and continued sending refresh
commands. This does not qualify its reconnect or automatic-startup behavior.

The first live 480×320 dashboard was started on the physical panel on August
17, 2026. It updated once per second and included CPU, memory, clock, and
available GPU telemetry. Missing GPU telemetry was handled without stopping
the display.

The installed service was subsequently migrated from the fixed renderer to the
versioned JSON widget renderer. The service loaded the 23-widget starter layout,
remained active, and continued producing a roughly 20 KiB dashboard frame.

Repeated dynamic uploads using both a leading and trailing `0x11` eventually
caused firmware 3.2 to stop accepting serial writes after about 35 seconds. Its
USB controller then stopped answering descriptor requests (`-110` timeouts) and
could not be recovered by USB authorization or `usbreset`; complete AC power
removal restored it. Static display plus keepalives remained stable beyond the
same interval. Automatic dashboard startup was disabled after this incident.
Further dynamic experiments use one refresh per subsequent frame and stop after
the first communication failure rather than reconnecting repeatedly.

After complete AC power removal restored the controller, the revised subsequent
frame sequence (`JPEG envelope | terminator | 0x11`) passed the former 35-second
failure point and continued for more than 100 seconds without a write timeout or
reconnect. Automatic startup remains disabled pending a longer qualification
and user confirmation of visual stability.

The initial dashboard tests exposed a device-specific commit behavior. A newly
uploaded frame remained dark until the next `0x11` command. Sending only a
leading refresh therefore revealed the previous frame briefly and then hid it
again during the next upload. Removing an experimental 100 ms delay made the
flash shorter, confirming that the delay was not the cause. The sender now adds
a second `0x11` immediately after each image terminator to reveal and retain the
new frame.

The corrected sequence was physically verified on August 17, 2026. The live
dashboard remained continuously visible while its clock, CPU, GPU, and memory
fields updated once per second. The user confirmed that the result was stable,
readable, and visually satisfactory.

The same corrected run later stopped after approximately 16 minutes with one
serial write timeout. Fail-stop behavior prevented any retry storm, but the
panel became blank. The `/dev/ttyACM0` node and stable `/dev/serial/by-id` link
disappeared even though the USB device, CDC ACM interface, and tty class entry
remained visible in sysfs. No USB reset was attempted after this result.

The user service was therefore disabled and remains outside accepted v1. A
subsequent manual test maintained refresh commands every second while reducing
full JPEG uploads from once per second to once every five seconds.

That reduced-load test was visually confirmed stable and updating, then passed
17 minutes without an
error—beyond the approximate 16-minute failure point of the one-frame-per-
second run. The serial device node and stable link remained present and USB
transactions continued increasing. The manual fail-stop process was left
running for a longer unattended observation; automatic startup remained
disabled.

The same run eventually timed out after approximately 49 minutes.
The panel became blank and stopped accepting writes, but remained fully
enumerated: `/dev/ttyACM0`, the stable by-id link, the CDC ACM interface, and
the sysfs USB records were all still present. Ubuntu recorded no kernel USB
disconnect or driver error around the failure. The service stopped after the
single timeout and did not reconnect. This establishes that reducing full
frames from one per second to one per five seconds delays but does not remove
the firmware-side long-duration failure.

## Confirmed USB-level stall defect

On August 18, 2026, the defect was reproduced again on the test host
after previously successful direct-driver and Panel Control activity. The
`/dev/ttyACM0` endpoint initially remained present, but serial writes timed out.
An existing tty node therefore does not prove that the panel is responsive.

A single controlled USB unbind/rebind was then attempted for the panel's USB
path. Rebinding did not recover the controller. The HONGTAI device continued
to appear in `lsusb`, but Linux no longer created `/dev/ttyACM0`, and the kernel
reported:

```text
usb <bus-port>: can't set config #1, error -110
```

This is a confirmed device/firmware USB-level stalled state, not merely an
application handshake failure. It can survive driver unbind/rebind while the
USB device remains superficially visible. Applications must stop after the
first communication failure and must not use rapid reconnects, repeated
unbind/rebind, USB reset loops, or descriptor/configuration retry storms to
hide the defect.

A complete cold power-cycle subsequently restored healthy firmware operation,
including the normal default animation and a working live JPEG path. The single
bounded exit-sequence test recorded above was then completed. Command `0x01`
was subsequently verified as the reboot-based route back to the default
animation. No non-reboot playback-selection command has been identified; do
not perform additional stream, reset, reconnect, or speculative media-command
tests without a separately reviewed procedure.
